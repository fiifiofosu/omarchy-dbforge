# Phase 4b — the Omarchy shell plugin

A native `bar-widget` plugin for the Quickshell-based shell, built to the
[Omarchy plugin development guide](https://plugins.omarchy.org/develop.html)
and verified against the running bar on Omarchy 4.0.3.

The plugin lives at the root of this repository, with DBForge under
`dbforge/`; these are the notes on building it. Why the layout is that way
round is the last section.

Phase 4 deferred this on the grounds that the install base was waybar-based.
That is no longer true: Omarchy 4.0 ships its own shell with a documented
plugin system, and `omarchy plugin` is how widgets are installed now. The
waybar module stays for 3.x; the two are alternatives, not companions.

## What the guide actually requires

The guide is short, and most of it the base classes give you for free. Worth
recording which parts are ours and which are not:

| Requirement | Where it is met |
|---|---|
| `manifest.json` with `schemaVersion`, `id`, `kinds`, `entryPoints` | `manifest.json` |
| Reverse-domain id, no `omarchy.*` prefix | `io.github.fiifiofosu.dbforge` |
| `open()` / `close()` / `toggle()` / `closeForPopoutSwitch()` | inherited from `qs.Ui`'s `Panel` |
| `opened` / `popoutSwitchClosing` properties | inherited from the same |
| Panel loaded internally, not declared as a second kind | `KeyboardPanel` inside `Panel.qml` |
| No symlinks in the plugin folder | `install.sh` copies |
| `omarchy plugin validate` passes | `make check` at the repository root |

The lifecycle methods are the part most likely to be reimplemented by mistake.
`qs.Ui`'s `Panel` already supplies all six, wired to the bar's popout
coordinator, so the entry point subclasses it and adds behaviour only. Writing
them by hand would work until the bar tried to switch popouts.

## `qmllint` on Arch is the wrong `qmllint`

`/usr/bin/qmllint` is the Qt 5 build. It reports **nothing** — not on
unqualified access, not on a file that does not parse:

```
$ printf 'import QtQuick\nItem { property int x: ; }\n' > bad.qml
$ qmllint bad.qml; echo $?
0
$ /usr/lib/qt6/bin/qmllint bad.qml
Warning: bad.qml:2:21: Member "x" shadows final member "x" ... [property-override]
```

So the Makefile names the Qt 6 binary explicitly. A check that silently passes
everything is worse than no check, because it is believed.

Even the Qt 6 one cannot resolve `qs.Ui` and `qs.Commons` — Quickshell's module
layout puts `module qs.Ui` in a directory called `Ui/`, which `qmllint` will
not follow — so every panel produces a cascade of import and unqualified-access
warnings. The baseline is what matters: Omarchy's own `dropbox/Panel.qml`
emits 139 warnings under the same invocation, in the same categories. This
widget's `Panel.qml` emits 129. The check is for a *new category*, not zero.

## `omarchy plugin enable` races its own discovery

The first install printed this:

```
WARN qml: PluginRegistry.setEnabled: unknown plugin io.github.fiifiofosu.dbforge
```

The installer had copied the files, enabled, then rescanned. The shell cannot
enable a plugin it has not discovered, so the order has to be rescan first.
That alone is not enough — discovery is asynchronous, and a rescan that has
returned is not a rescan that has finished — so `install.sh` retries the enable
for a few seconds. With both fixes a clean install logs nothing at all.

## The PATH trap, again

Same failure as Phase 4, same cause. The shell is started by the systemd user
manager, whose `PATH` has no `~/.local/bin` because user services never source
`~/.bashrc`. A `Process` whose command is a bare `dbctl` finds nothing, and the
widget renders empty with no error anywhere.

The waybar module solved this by writing absolute paths into the config at
install time. That does not transfer: a QML plugin's settings are edited in the
Omarchy UI, not generated by an installer. So `Service.qml` resolves the binary
itself on startup, checking `$DBFORGE_DBCTL`, `~/.local/bin`, `/usr/local/bin`,
`/usr/bin` and then `PATH`, with a manifest setting to override. When nothing
is found the panel says so instead of sitting blank.

## Polling, not signals

Phase 4's widget is signal-driven: `dbforged` sends `SIGRTMIN+8` and waybar
refreshes. A QML plugin has no equivalent — it shares the shell process, and
having a plugin install a signal handler in the bar would be a hazard for
every other widget.

So this one polls, at 10 seconds by default, and refreshes whenever the panel
opens and after every action it takes. The cost is one short-lived `dbctl`
per interval; the alternative is a socket client inside the shell process,
which is a lot of surface area for a value that changes a few times a day.

## What is not in the panel

Create and destroy. Both are destructive enough to want a typed confirmation,
which is what the TUI has and a bar panel does not. The panel does start, stop,
and copy a connection string, and `t` opens the TUI for the rest — the same
line the waybar right-click menu draws.

A `missing` instance gets no switch at all. Its container has been removed
behind the daemon's back, and offering to start it would suggest the widget can
repair drift, which it cannot.

## Testing

`Model.js` — parsing, sorting, counting, row text — is plain JavaScript and is
tested directly (`model_test.mjs`, 21 cases). That is
deliberate: the interesting states are a daemon that is down, a container that
vanished, and an instance that exited 137, and driving the live widget into
those would mean stopping real databases.

The test is skipped rather than failed when `node` is absent, since node is not
otherwise a dependency of this project.

Runtime behaviour was verified against the live shell through the plugin's own
IPC handler, which is also the reason it declares one:

```
$ omarchy-shell io.github.fiifiofosu.dbforge status
2 running
$ dbctl list | tail -n +2 | wc -l
2
```

`toggle`, `refresh` and `close` were exercised the same way, with a clean
journal afterwards.

## Why the plugin is at the repository root

The widget was built inside DBForge's tree, under `packaging/omarchy-plugin/`.
It could not stay there. `omarchy-plugin-add` is the install path, and it does:

```bash
git clone -- "$url" "$stage"
omarchy-plugin-validate "$stage"
id=$(jq -r '.id' "$stage/manifest.json")
mv "$stage" "$target"
```

The manifest has to be at the **root** of the cloned repository; there is no
subdirectory argument, so a plugin nested inside a larger tree cannot be
installed at all.

That leaves two ways to satisfy it, and this repository has been both. It was
briefly its own repository, with DBForge referenced from the README. It is now
one repository with the positions swapped: the plugin at the root, DBForge
vendored under `dbforge/`. The second shape was chosen so that everything the
widget needs is in one public place rather than behind a link.

The cost is visible and worth stating: `mv "$stage" "$target"` makes the clone
*become* the plugin folder, so installing the widget puts this Go source into
`~/.config/omarchy/plugins/io.github.fiifiofosu.dbforge/`. It is 804K and the
shell never loads it — it reads only the files named in `entryPoints` — but it
is there.

Verified through the real path against the published repository:

```
$ omarchy plugin add https://github.com/fiifiofosu/omarchy-dbforge --enable --yes
Added io.github.fiifiofosu.dbforge into ~/.config/omarchy/plugins/io.github.fiifiofosu.dbforge
Enabled io.github.fiifiofosu.dbforge
$ omarchy-shell io.github.fiifiofosu.dbforge status
2 running
```

## Consent, for the marketplace checklist

The submission checklist requires that a plugin "does not overwrite user
configuration without explicit consent". Enabling a widget writes to
`~/.config/omarchy/shell.json` and puts it on the bar, and the first
`install.sh` did that unconditionally.

Copying a plugin in is not the same decision as turning it on, so the two are
now asked separately — which is also where `omarchy plugin add` draws the line,
with its own "Enable '$id' now?" prompt. The clone installer prompts, takes
`--enable`/`--no-enable`, and defaults to installing without enabling when
there is no terminal to ask in.
