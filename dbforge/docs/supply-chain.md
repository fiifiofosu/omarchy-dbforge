# Supply chain

Two findings from the security review of commit `4bf66cbf` said the same thing
twice: a mutable pointer was deciding which code ran on a user's machine. This
is what was changed, and what remains true afterwards.

Neither finding was about a missing integrity check. Both were about *what the
integrity check was anchored to*.

---

## 1. Engine images

**What was wrong.** `internal/engines/engines.go` accepted any registry tag,
and `internal/daemon/manager.go` built `docker.io/library/<engine>:<tag>` from
it, pulled that, and ran it:

```go
image := eng.Image + ":" + version
```

A tag is a mutable pointer. `postgres:16` names whatever the library
maintainers last pushed under that name. An instance created in six months from
the same DBForge build would therefore run different code from one created
today, and neither need be the code anyone reviewed. Pulling a tag means
executing whatever the registry chooses to serve at pull time.

**What it is now.** Every image DBForge can run is listed in
`internal/engines/pins.go` against the digest of its manifest index, and that
file is generated by `scripts/update-pins.sh` (`make pins`). The tag survives
only as the name a user types and as the version the catalogue reasons about --
the Postgres 18 layout change, the host directory mode. It never reaches the
runtime:

- `engines.ParseRef` refuses a version that is not pinned, returning
  `UnapprovedVersionError`, before a container, a data directory or a port
  exists. An unapproved version costs the user an error message and nothing
  else.
- `Engine.PinnedRef` is the only way to obtain an image reference, and it
  returns `image@sha256:...` or an error. There is no fallback to the tag,
  because a fallback is the hole itself.
- `Manager.Create` pulls, runs and persists that reference. `dbctl list --json`
  reports the digest each instance is actually running.
- The multi-arch *index* digest is what is pinned, so one pin is correct on
  every architecture.

**The reviewed upgrade path.** Approving a version is a two-part change that
lands as a diff: add the tag to `APPROVED` in `scripts/update-pins.sh`, run
`make pins`, and send the resulting change to `pins.go` to review. Withdrawing
one is the same in reverse. Nothing resolves a tag at runtime, so there is no
point at which an unreviewed digest can enter.

**The cost, stated plainly.** A new upstream release is not available the day
it ships, and a user cannot create `postgres:17.2` or `redis:7-alpine` on a
whim. That is the trade the review asked for: what DBForge runs is now a
property of the reviewed build rather than of the registry's current state.

**Knock-on simplification.** The TUI used to fetch a version list from Docker
Hub, cache it, and warn when it might be stale. The offerable set is now known
at build time, so `internal/registry` is gone: the list is compiled in, needs
no network, is identical on every machine, and is exactly the set `create` will
accept.

## 2. The self-updater

**What was wrong.** `internal/update/update.go` selected `releases/latest`,
then downloaded that release's binaries *and* its `SHA256SUMS`, verified one
against the other, and replaced the installed executables.

The checksum was real and it did catch a download that did not match what the
release listed. But both halves were chosen the same way -- whatever
`releases/latest` pointed at that minute -- so anyone able to publish or alter
a release published both. The check could prove the two agreed with each other;
it could never prove that either was the artifact anyone had reviewed. A
program that replaces its own executable on that basis is a supply-chain hole
whatever it hashes on the way in.

**Why it was not fixed by pinning instead.** Binding the download properly
means an expected digest or signature fixed *independently* of the release
being fetched. For a version that does not yet exist when the running binary is
built, there is no honest way to do that without a signing key and signature
verification this program does not have. Requiring an explicit `--version`
whose hash is compiled in would be genuinely immutable and close to useless: a
build could only ever update to versions that already existed when it was
built.

**What it is now.** The downloader is removed, not fixed. `internal/update`
reads a version number and a release URL, and that is all it can do:

- `Release` carries `Tag`, `Version` and `URL`. It holds no asset URLs, and a
  test asserts that none reach the caller even when the API offers them.
- The package writes nothing to disk and executes nothing. `os.Rename`,
  `os.MkdirTemp` and `exec.CommandContext` are gone with the installer, and the
  baseline script fails if any of them return.
- `dbctl update` and the TUI's `u` key report whether a newer release exists
  and print the command to install it. `--check` is accepted and ignored, since
  checking is all the command does.

Installing is the package manager's job, which verifies packages against keys
the user has decided to trust.

## Evidence

`make security-baseline` re-establishes both properties mechanically against
the tree as committed and writes `dist/security-baseline.txt`. It refuses to
certify a dirty working tree, because evidence that does not describe a
specific commit is not evidence. It checks that:

1. every pin is a digest, and every one of them still resolves against the
   registry;
2. no code joins an image to a tag, and only `Manager.Create` pulls at all;
3. `internal/update` neither writes to disk nor executes anything, handles no
   asset URLs, and is the only package that contacts the release API;
4. `make vet`, `make test` and `make build` pass.

Both source checks were confirmed against the pre-fix code: each one matches
the exact lines the review cited. The baseline runs as a CI job on every change
and uploads its output, so a regression fails the build rather than waiting for
the next review.

The Go suite covers the same ground where it belongs:
`TestCreatePullsAndRunsByDigestNotByTag`,
`TestCreateRejectsAnUnpinnedVersionBeforeTouchingAnything`,
`TestEveryPinIsAWellFormedDigest`, `TestReleaseCarriesNothingDownloadable`,
and `TestEveryOfferedVersionIsCreatable`, which keeps the form's list and the
approval set from drifting apart.
